# Практики Markdown, local-first и AI-контекста

Дата исследования: 2026-09-07  
Область: официальные спецификации, официальная документация и открытый исходный код. Рекламные обзоры не использовались.

## Краткий вывод

Зрелые Markdown/local-first продукты обычно выигрывают не количеством возможностей, а быстрым
возвратом к заметке: поиск, теги/папки, ссылки, список недавних файлов и дата создания.
Календарь не является обязательной отдельной подсистемой: ежедневная заметка с именем
`YYYY-MM-DD` и простой группировкой/фильтром по дате уже покрывают сценарий «вернуться к
периоду». Для Memoroid разумно сначала сделать компактный навигатор периода (дата/месяц,
список заметок), а не календарь-сетку.

Машиночитаемое соглашение должно быть небольшим и переносимым: CommonMark/GFM для текста,
опциональный YAML front matter для `title`, `date`, `tags`, `aliases`. Front matter следует
сохранять без потери и не делать обязательным: исходный Markdown остаётся источником истины.
AI-контекст лучше хранить в обычном `AGENTS.md`/`CONTEXT.md` рядом с кодом и явно описывать
правила, команды проверки и границы изменений; не прятать его в базе приложения.

На mobile хороший минимальный UX означает один явный primary action «новая заметка»,
быстрый поиск, список с крупными строками и редактор без перегруженной панели; чтение и
редактирование должны работать без сети. Это вывод из возможностей и структуры официальных
продуктов, а не универсальная UI-спецификация.

## Источники и конкретные факты

### Формат Markdown

* [CommonMark Specification](https://spec.commonmark.org/current/) — формальная
  однозначная спецификация Markdown и тесты; она определяет базовые блоки (заголовки,
  списки, цитаты, fenced code, ссылки), но не определяет YAML front matter и wikilinks.
  **Вывод:** рендерить и сохранять базовый Markdown без вендорных расширений; расширения
  должны быть явно опциональными.
* [GitHub Flavored Markdown Spec](https://github.github.com/gfm/) — GFM основан на CommonMark
  и добавляет таблицы, strikethrough, task list items и autolinks (среди прочего).
  **Вывод:** поддержка task list полезна для заметок, но не должна требовать GitHub или
  сервера; таблицы можно оставить совместимой будущей возможностью.

### Front matter и метаданные в продуктах

* [Joplin: Markdown + Front Matter importer/exporter](https://joplinapp.org/help/dev/spec/interop_with_frontmatter/)
  — описывает YAML-блок метаданных в начале документа и отдельный importer/exporter,
  совместимый с Markdown importer/exporter. **Вывод:** metadata block — практичный
  interoperability-слой, но отдельный режим обмена; нельзя предполагать, что любой Markdown
  обязан иметь YAML.
* [Obsidian Help: Properties](https://obsidian.md/help/properties) — properties содержат
  структурированные значения, включая текст, links, dates, checkboxes и numbers.
  **Вывод:** для Memoroid достаточно узкого белого списка (`title`, `date`, `tags`,
  `aliases`), а неизвестные поля нужно сохранять и показывать как есть.
* [Quartz: Authoring Content](https://quartz.jzhao.xyz/getting-started/authoring-content)
  — официальный генератор читает frontmatter для `title`, `tags`, `aliases`, `cssclasses`;
  date, description и другие значения обслуживаются отдельными plugins. **Вывод:** даже
  зрелая система разделяет parsing метаданных и функции представления; Memoroid не должен
  связывать наличие `date` с обязательной публикацией или плагинной архитектурой.

### Возврат к периоду и календарный сценарий

* [Obsidian Help: Daily notes](https://obsidian.md/help/plugins/daily-notes) — daily note
  по умолчанию создаётся с сегодняшней датой в формате `YYYY-MM-DD`; папка и формат
  настраиваются. **Вывод:** стабильное ISO-имя даёт сортировку и возврат к дню без календаря.
* [Obsidian Help: Backlinks](https://obsidian.md/help/backlinks) — backlinks показывают
  ссылки на активную заметку. **Вывод:** ссылки и обратные ссылки полезны как лёгкая
  навигация, но граф и сложная сеть не нужны для базового возврата к периоду.
* [Logseq documentation](https://docs.logseq.com/) — документация отдельно описывает
  Journals page, pages, создание графа из существующих Markdown-файлов, indentation и
  linking. **Вывод:** журнал по датам — самостоятельный понятный вход, а links/blocks —
  следующий слой; не следует превращать просмотр заметок в обязательную графовую модель.
* [Joplin help](https://joplinapp.org/help/) — приложение организует большое число заметок
  в notebooks, поддерживает поиск, копирование, теги и изменение заметок; официальная
  документация также покрывает desktop и mobile. **Вывод:** поиск + плоский список/папки +
  теги — проверенный минимальный набор до календаря.

Решение для Memoroid: календарь-сетка оправдан только если пользователь часто мыслит
«какие записи были в этот день» и одного списка дат недостаточно. Сначала достаточно:
`date` из front matter или даты файла, сортировка по дате, фильтр «месяц/диапазон» и
список найденных файлов. Это работает из `file://`, не требует индекса на сервере и
допускает отсутствие метаданных. Календарь можно добавить как представление того же
индекса, не меняя формат файлов.

### AI-agent context patterns

* [AGENTS.md format repository](https://github.com/agentsmd/agents.md) — открытый формат
  `AGENTS.md` предназначен для инструкций coding agents; пример и спецификация находятся
  в публичном репозитории. **Вывод:** имя файла, обычный Markdown и расположение рядом с
  проектом — переносимее, чем проприетарная база контекста.
* [AGENTS.md example/source](https://github.com/agentsmd/agents.md/blob/main/AGENTS.md) —
  репозиторий показывает, что файл может задавать область действия и инструкции для
  работы с проектом. **Вывод:** контекст должен явно содержать правила, команды build/test,
  структуру и ограничения, а не только длинное описание проекта.
* [GitHub Copilot: AGENTS.md custom instructions changelog](https://github.blog/changelog/2025-08-28-copilot-coding-agent-now-supports-agents-md-custom-instructions/)
  — GitHub сообщает о поддержке `AGENTS.md` для того, чтобы направлять агента в понимании
  проекта, сборке, тестировании и проверке изменений. **Вывод:** эти четыре раздела —
  хороший минимальный шаблон для `CONTEXT.md`/`AGENTS.md`; это локальный текстовый файл,
  не внешний сервис.
* Текущие инструкции Memoroid уже используют `AGENTS.md`, `CONTEXT.md` и
  `docs/agents/`. **Вывод для проекта:** не добавлять второй конкурирующий формат
  (например, JSON-кэш AI); документировать precedence и область действия обычных файлов.

### Mobile UX

Прямой первичный стандарт «mobile UX для Markdown-заметок» у рассмотренных проектов не
обнаружен. Поэтому ниже только практические выводы из официальных возможностей, без
претензии на нормативность:

* [Joplin Help](https://joplinapp.org/help/) позиционирует один продукт для Windows,
  macOS, Linux, Android и iOS и перечисляет поиск, notebooks, tags и редактирование.
  **Вывод:** эти операции должны оставаться доступными на узком экране и офлайн; desktop
  функции не должны быть обязательными для чтения/записи.
* [Joplin Markdown guide](https://joplinapp.org/help/apps/markdown/) описывает Markdown
  как простой текстовый формат, который хорошо выглядит на любом устройстве и оставляет
  только основные средства форматирования. **Вывод:** на mobile предпочтительны plain-text
  ввод, короткая панель часто используемых действий и preview, а не визуальный конструктор.
* [Logseq documentation](https://docs.logseq.com/) выделяет Journals и indentation.
  **Вывод:** mobile entry point может быть «сегодняшняя запись» и быстрый capture, но
  вложенные блоки не следует навязывать Memoroid до подтверждённой потребности.

## Рекомендации для Memoroid

### Взять

1. Полнотекстовый поиск по локальным Markdown-файлам.
2. Сортировка по modified/created date и фильтр по ISO-дате или диапазону.
3. Опциональный YAML front matter с малым стабильным словарём: `title`, `date`, `tags`,
   `aliases`; сохранение неизвестных ключей.
4. Теги, папки и список недавних файлов; отсутствие метаданных не должно ломать заметку.
5. Markdown task lists и ссылки CommonMark/GFM; безопасное отображение и сохранение
   оригинального текста.
6. Mobile layout: крупные touch targets, одна кнопка новой заметки, быстрый поиск,
   readable list/editor, видимый статус сохранения и offline-first поведение.
7. Единый текстовый `CONTEXT.md`/`AGENTS.md` с правилами, проверками и границами.

### Отложить

1. Календарь-сетку — до появления данных/запросов, показывающих, что диапазонный список
   неудобен.
2. Backlinks — после базовых Markdown links и устойчивых путей файлов.
3. Wikilinks, aliases с неоднозначным разрешением, graph view.
4. Полный набор frontmatter-полей, запросы по свойствам, block references.
5. Синхронизацию, аккаунты, плагины и внешний AI-сервис.

### Не брать

1. Обязательную базу данных или индекс, без которого невозможно открыть `index.html`
   напрямую.
2. Формат, который заменяет исходный Markdown внутренним JSON/HTML.
3. Обязательный YAML/front matter или обязательные vendor-specific wikilinks.
4. Сложную dashboard-навигацию и календарь ради календаря.
5. Плагинную платформу как условие базового просмотра и редактирования.

## Ограничения и проверка применимости

Все предложенные первые функции совместимы с Windows и `file://`, если чтение файлов
остаётся в уже предусмотренном fallback-режиме, а каталогный режим остаётся опциональным.
Дата должна вычисляться с понятным precedence (например, front matter `date`, затем дата
файла/mtime), а запись не должна молча переформатировать Markdown. Перед реализацией
нужны тесты на файл без front matter, неизвестные YAML-ключи, невалидную дату, task list,
Unicode-пути и работу без сети.
